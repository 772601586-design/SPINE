# 方案自动识别、视频对应与每日日程

当前工作区运行 `miniprogram-demo/`。底部入口依次为「制定、训练、社群、我的」。

## 使用流程

1. 「制定」左侧相机直接录制示范，填写动作名称与现场要点，视频保存在左侧。
2. 右侧文件夹选择康复师方案。支持 JPG/PNG、PDF、DOCX、TXT；旧 DOC 依赖本机安装 Word。
3. 系统提取原文中的动作名称、组别、组数、每组次数/秒数/呼吸次数、要点、训练频次，生成下面的动作卡。原文件和对应原文保留，可通过「核对文字与动作」修正。
4. 名称规范化后只有唯一对应的动作和录段才自动关联。左右侧、体位等有意义的差异保留；多个同名录段不自动选择。打开动作卡的「关联视频」可以手动对应，不替换动作名或训练量。
5. 训练量完整、频次明确的动作自动进入计划；「训练」按选择的日期显示当天清单，按组别展示。

例如「靠墙站姿练习，3组，每组30秒，每天」会生成动作卡，并每天出现在训练清单中。如果视频名称也为「靠墙站姿练习」，且只有一个对应录段，会直接关联。

## 日程规则

| 文件内容 | 当前处理 |
|---|---|
| 每天/每日一次 | 每天安排 |
| 隔天/隔日 | 从导入日期起按日历间隔一天安排 |
| 每周一、三、五 | 对应星期安排 |
| 每周三次，没有指定日期 | 动作卡保留，日程待补充 |
| 每天多次，没有分时安排 | 动作卡保留，日程待补充 |
| 未注明组数、每组量或单位 | 缺失字段留空，动作待补充 |
| 一组内出现冲突的训练量或频次 | 保留原文并提示核对 |

现有手动计划的隔天逻辑保留。重试同一原件不重复生成；同名且识别文字相同的重复上传复用已整理的动作。历史训练记录保存当时的训练量快照，后续资料更新不覆盖历史完成量。

## 本机运行

在项目根目录执行：

```powershell
node scripts/serve-demo.cjs
```

该进程提供本地预览及 `http://127.0.0.1:4180/api/recognize-scheme` 文件识别服务。PDF/Word/TXT 优先读取原生文字；扫描 PDF 渲染后使用 Windows OCR，图片直接使用 Windows OCR。文件在本机处理，不调用外部识别平台。PDF/Word 解析依赖本机 Python（pypdf、pypdfium2）；可通过 `XIAOSHU_PYTHON` 指定 Python 路径。

关键代码：

- `miniprogram-demo/core/document-recognition.js`：小程序文件读取与识别请求。
- `scripts/scheme-file-recognition.cjs`：文件校验、解析、OCR 与临时文件清理。
- `miniprogram-demo/core/documents.js`：按原文提取动作和明确的训练要求。
- `miniprogram-demo/core/scheme-import.js`：稳定动作标识、视频关联、自动计划、重试与历史保护。
- `miniprogram-demo/pages/planning/index.js`：上传、识别进度、文件区域和动作卡展示。
- `miniprogram-demo/pages/train/index.js`：读取计划并展示所选日期的清单。

## 正式手机版本需要接通的部分

目前识别服务位于本机，训练数据存于小程序本地存储。手机正式版需要把识别服务部署到手机可访问的 HTTPS 后端或云函数，并把原文件、动作、视频关联、计划和完成记录保存到对应用户的数据中。

仓库已有 Django 后端的附件、OCR、处方导入、个人动作卡和每日清单模块（`backend/life/ocr.py`、`backend/life/prescriptions.py`、`backend/training/scheduler.py`）。它们目前与本次 demo 自动导入流程分开，不能仅替换 URL 就视为完成上线；仍需统一字段、导入幂等标识、视频对应和日程语义，并验证真实手机上传与识别。

当前提取器基于明确的文字结构和规则，任意排版、手写、模糊扫描件仍可能需要校对。若后续加入模型解析，应要求输出相同字段与原文定位，继续保留缺失值和冲突状态。
