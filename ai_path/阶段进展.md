**刻意做对的地方**

- **不拿 1 月 1 日冒充"日期不详"**：三者互斥由 `CheckConstraint` 在库层兜底，不只是序列化器校验。
- **"日期不详"的就诊排序排最后**：PostgreSQL 在 DESC 下默认 NULLS FIRST，不写 `nulls_last=True` 会让未知日期冒充"最近一次就诊"。
- 附件必须是 `medical` 用途、属于本人、已完成上传，且**一张附件只能属于一次就诊**（唯一约束 + 显式 409）。
- 并发绑定用 `select_for_update` 锁住就诊行，数量上限不能被并发绕过。
- 解绑 ≠ 删原件：附件仍是本人私有对象（医疗用途不对他人开放），由孤儿清理任务兜底。
- DRF 的 `@action` 同一路径只能注册一个：PATCH/DELETE 与 GET/POST 各自合并到一个方法里，否则第二个方法会变成 405。

3. 就诊：`POST /visits/` 三态日期（day/month/unknown 互斥）→ `POST /attachments/upload-intent/`（purpose=medical，JPG/PNG/PDF，≤20MB）→ 传字节 → `complete` → `POST /visits/{id}/attachments/` 绑定分类。

**刻意做对的地方**

- **日期不撒谎**：界面把 `month` 显示成「2025-03（仅年月）」、`unknown` 显示成「日期不详」，都不渲染成某一天；选「不详」时不往库里写任何日期字段。

- **测量不在档案上留副本**：身高体重只有一种真源，避免「档案里的体重」和「最近一次测量」长期对不上。
- **删除就诊是危险操作**：二次确认 + 明确告知「资料不再可读、计划侧显示原记录已删除」。

**为什么是这两个手段**

- **配额挡滥用**：`upload-intent` 即建行，不限流就是零成本刷行接口；只数 pending，正常「传完没 complete」的并发不受影响。
- **TTL 兜底清理**：中途放弃、断网、魔数复核拒绝都会留下 pending 孤儿，没有清理任务它们永远在。
- **刻意不进后台**：后台能看到文件名就等于能看到「谁上传了什么」，与隐私边界冲突；只能走管理命令。

```bash
cd D:/SPINE/backend
./.venv/Scripts/python.exe manage.py cleanup_attachments --dry-run   # 先看会删什么
./.venv/Scripts/python.exe manage.py cleanup_attachments             # 正式清理（可加 cron/计划任务）
```
