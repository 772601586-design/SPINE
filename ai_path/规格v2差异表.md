## 一、结论摘要

现有仓库是「Flutter 迁移到小程序」阶段的产物，已具备**可用底座**（Django+DRF+PostgreSQL、微信登录、Token 会话、支具计时闭环、小程序原生 TS 工程、28 个后端测试）。

v2.0 要求的产品结构中，**约 60% 是全新领域**：动作库与多维分类、周期计划与排程引擎、游泳记录、医疗档案与私有附件、社区内容审核、通知与成就。这些后端**完全没有对应模型**。

**没有任何一项需要推倒重来**；但导航结构（4 Tab → 3 Tab）和支具数据模型需要改造，且这两个动作会动到目前唯一跑通的业务闭环。

## 五、风险与注意事项

1. **M1 与 M2 会动到唯一跑通的业务闭环**（支具佩戴）。改造期间该功能需保持可用，不可先删后建。
2. **M3 API 契约变更影响所有接口**。集中式 renderer 可避免逐个改 viewset，但小程序 `request.ts`、`verify_miniprogram_client.py`、`verify_flutter_client.py` 三处消费方要同步。
3. **支具跨午夜切分**（§9.2、T18）是统计正确性的核心。已有时区处理在 `WearSession.original_timezone`，需改为「发布后保留目标时区，不因手机切换重算」。
4. **§6.5 的统计口径命名**（周期进度 / 已到期完成率 / 按时完成率 / 补做数）必须严格区分，不得混成一个百分比。
5. **不做每日打卡**：现有 `today` 页与提醒逻辑里的每日假设要一并清除，不能只改名。
