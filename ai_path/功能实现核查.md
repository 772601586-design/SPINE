# spine1 功能实现核查

这是补齐前的核查快照。后续正式端变更见《缺失功能补齐记录》，当前按用户最新要求运行的源 demo 复现见《原始小程序demo复现》。

核查日期：2026-10-16。范围：`spine1/design/功能` 的功能总览及 18 项功能说明，对照原始 demo、`miniprogram/prototype` 演示分包、正式小程序与 Django 后端源码。

## 结论与口径

**没有全部实现。** 功能总览中的“已实现”指原型 v3 可体验，不代表正式小程序已接入真实数据和服务。此前的“完整 demo 复现”完成了原始 18 个页面的移植，不能据此认定功能说明全部完成；原始 demo 本身也存在未闭环的交互。

按正式小程序核查：9 项部分实现，7 项尚未实现，1 项待医生确认，1 项属于已遵循的产品决定。这里按整项需求判断，不把一个入口或一个展示页面算作整项完成，也不计算完成百分比。

本次为源码和需求逐项核查，不等同于微信真机验收、实际 OCR 服务验收或医疗内容审核。未修改业务代码。

## 主要源码依据

- `backend/config/urls.py`：已注册档案、支具、体测、就诊、动作卡及训练记录等接口；未见 OCR、社群、积分、提醒或游泳业务接口。
- `backend/training/scheduler.py`：个人逐卡每日/隔次安排，以已确认的完整训练记录计算；不等同于功能说明中的整套模块交替规则。
- `miniprogram/services/local-recordings.ts` 及 `pages/rehab/recordings`、`pages/rehab/match`：真实本地视频管理与手动匹配。
- `miniprogram/pages/rehab/follow/index.ts`、`index.wxml`：组数确认与恢复流程已接入；页面明确提示语音播报服务尚未接入。
- `miniprogram/pages/rehab/activity/index.ts`：游泳入口仍为提示。
- `backend/medical/models.py`、`miniprogram/pages/personal/visits/detail`：手动就诊/测量与附件流程；模型明确不做 OCR。下次复查日期不构成提醒系统。
- `miniprogram/pages/growth/index.ts`：当前主要呈现体测及就诊列表，未实现完整曲线和复查摘要。
- `backend/braces/models.py`：有支具及佩戴相关数据基础，但支具缺处方目标时长及传感器接入字段。
- `miniprogram/pages/community/index.wxml`、`pages/personal/index.ts`：社群与多个个人中心入口尚未开放。
- `backend/profiles/serializers.py`、`miniprogram/pages/onboarding/profile`：自定义性别输入校验和初潮展示条件仍需与设计对齐。

## 演示本身也需要补齐的交互

以下问题同时影响“完整 demo 已复现”的解释：页面可以移植完整，但不代表设计列出的输入、计算和保存均已实现。

1. 原始 `spine1/demo/miniprogram/pages/import/index.wxml` 的处方参数输入框未绑定输入事件，不能把用户修改保存回状态。
2. 原始 `spine1/demo/miniprogram/pages/upload/index.wxml` 的报告字段同样未绑定输入事件，保存流程使用示例数据。
3. 原始欢迎页出生年月及自定义性别输入没有完整输入绑定。
4. `miniprogram/prototype/core/spine-app.js` 的跟练时间、次数和呼吸提示是固定展示，未执行真实倒计时及节奏播报。
5. 同一演示核心中的复查摘要仅弹出提示；提醒开关不产生真实定时提醒；绘画操作未形成图片保存流程。
6. 演示支具小时数为固定值，点击状态不形成真实佩戴时间统计；积分与补签属于示例状态变更。
7. 演示中的成人卡组仍固定取四个动作，与功能说明中“沿用本人处方”的要求有差异。

## 建议实施顺序

1. 先补演示可见交互：所有编辑输入回写、真实倒计时/计数、报告与处方保存、复查摘要和绘画保存，避免按钮只有提示。
2. 再补正式核心闭环：处方手动导入/校对及变更记录、跟练节奏、成长趋势与复查准备、支具目标、成人记录；OCR 作为明确服务接入单独验收。
3. 经医生确认模块与内容后，补复查提醒、游泳、学习及积分勋章；社群单独落实内容与治理规则。

未确定的医生规则、传感器协议、手表心率和积分经济规则不能用演示常量代替最终需求确认。
